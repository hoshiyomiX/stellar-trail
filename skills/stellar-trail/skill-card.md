## Description:

Stellar Trail 🌠 defines a mandatory six-phase execution protocol and persistent memory lifecycle for agents so work can be classified, clarified, planned, executed, validated, reported, and restored across sessions. Phase 1 classification is grounded in a canonical Ground Base Knowledge (type taxonomy, language rules, complexity calibration, ambiguity registry, environment ground truths) so every decision cites a rule ID instead of intuition. Phase 5 validation runs five review layers (artifact verification, smoke, lint, request-vs-deliverable diff, regression) before anything is reported, and enforcement is dual-track: terminal-verifiable rules are executed via the bundled gate script (enforce-gates.sh), judgment rules stay as text mandates — a claimed-but-not-run gate is itself a violation. Since v2.0.1 the skill carries an explicit activation rule: a description in a skill list is not activation — agents load the full protocol body at the first turn of every session or continuation, then display auditable phase and memory markers on every response. Memory is user-controlled by design: plain-file storage, a cold-start consent gate, a strict no-secrets minimization rule, same-turn inspect, correct, redact, delete and purge commands, and an explicit owner opt-out that differs from hurry pressure (SKILL.md section 4b, rule 13).

Since v3.0.0 (formerly stellar-trails @ClawHub, renamed from workflow-memory-guardian) every phase marker carries a 🌠 — a visible, countable proof that the protocol is running.

Since v3.1.0 the skill also bundles the Task Files Explorer as a built-in optional asset (assets/explorer/ — stdlib Python server, MD3 adaptive UI, launcher, boot-hook template): a functional replacement for the platform file popup, served on the preview URL, localhost-bound, Next.js-aware, and deployed only on explicit request — the same consent discipline as the rest of the protocol.

Since v3.2.0 phase markers render as markdown sub-headings (`## FASE n 🌠 — LABEL`) — larger than normal text so the audit trail is scannable at a glance — and every documented script invocation is exec-bit-independent (`bash`/`python3`), matching registry installs that normalize file permissions to 0644.

Since v3.3.0 the skill bundles its own repair mechanism: heal-skill.sh verifies the installation against a SHA-256 manifest shipped with the release (missing, damaged, and extra files, plus rolled-back _meta versions, are all detected without any external source) and repairs it from the healthiest available source — a local canonical copy, the platform restore archive, or as a printed manual fallback the ClawHub registry. The same release removes the former shadow-backup layer after empirical findings showed its stale-detection produced false-positive restore attempts, shared the same blind spot and failure domain as the archive it guarded, and burned significant write bandwidth; the playbook now relies on refresh-the-source, self-heal, and reversible original-backup layers, each tested end-to-end. The bundled Task Files Explorer gains a guardian status card (skill version, last heal, watcher state), per-file quick download, copy-path, relative timestamps, focus-triggered refresh, and attachment-mode downloads. Since v3.3.1 the drift check falls back to a source-based two-way comparison when the manifest itself was destroyed by the degradation (the real incident wiped assets/ including the manifest), so the default check keeps working in exactly the scenario it was built for. Since v3.4.0 the 🌠 leads the marker text (`## 🌠 FASE n — LABEL`) and every marked turn opens with a protocol banner carrying the skill name and version — the user always knows which protocol version is enforcing the response, and an older-than-expected banner version is the visible signature of a degraded installation, cueing the bundled self-heal check. The former TRAIL closing line (v3.0.0 through v3.3.1) is retired in v3.4.0: the sub-heading phase markers are themselves the complete, countable audit trail. Since v3.5.0 memory hygiene makes stale-task pickup structurally impossible (SKILL.md section 4d): the SESSION-STATE task table is ACTIVE-only (ACTIVE/BLOCKED rows), completing or cancelling a task seals it out of the table in the same atomic write into a compact Sealed list (last five entries, one line each), sealed tasks are never resurrected (a revision opens a new Task ID referencing the old one), and active tasks with no material progress for over 72 hours or spanning two session boundaries are flagged STALE and require explicit user reconfirmation before resumption — the memory now never lies about what is still alive. Since v3.5.1 the quarantine extends to the one input the memory does not control: platform continuation summaries. A stale summary (in the founding incident it was frozen four releases behind) narrating sealed tasks as pending can no longer trigger re-execution — its version claims are grounded against memory files and the installed skill, "continue with the last task" resolves via the Active table only, summary-vs-memory conflicts are reported in the first response, and the Active table is never seeded from a summary; an M0 version-sanity alarm also flags degraded installations (installed banner older than the recorded release) before the body is trusted. Since v3.5.2 the bundled self-heal is location-aware: the ClawHub CLI installs new skills owner-scoped (skills/@owner/stellar-trail) while older installs sit flat (skills/stellar-trail), and heal-skill.sh now verifies and repairs BOTH layouts — its canonical-source resolution walks up multiple directory levels so an owner-scoped install finds its source, the registry hint prints the actual lock key read from the local clawhub lock file, a wiped installation is rebuilt complete with its clawhub metadata, and a sourceless check that cannot verify anything fails loudly with a non-zero exit instead of passing silently. Since v3.5.3 the self-heal is pin-aware and age-aware: it reports the ClawHub pin state of every skill in the local lock file (a pinned skill blocks its own clawhub update/install and is silently skipped by update --all, so the report warns with the exact unpin command while drift verdicts and exit codes stay untouched), flags a healthy-but-older installation against a newer canonical copy (deliberate --force remains the only upgrade path), and labels which repair source won (env, walk-up, platform default, or restore archive) without changing the multi-source order. Since v3.5.4 the repair chain is vault-aware and version-aware: a class-A skill vault (synced to /home/sync/skill-vault and the ossfs upload/ mount by the new bundled vault-sync.sh on every publish, with a symmetric anti-downgrade assert on both writer and reader sides) joins the canonical-copy and restore-archive repair sources, source selection picks the highest verified version, and an anti-downgrade assert skips any source older than the installed release — a stale restore can no longer silently roll a healthy installation back, and a wiped installation is rebuilt from the freshest surviving copy. The same release ships Explorer UI v3.0 (live search with 200 ms debounce, dynamic category filter chips with per-category counts, column sorting, per-card copy-path with toast feedback, adaptive dark/light theme following the system preference until a manual choice is saved, file-type icons, chunked lazy rendering with IntersectionObserver, event delegation, and explicit loading/empty/error states), documents the verified boot forensics of Tasks 36–38 as auditable receipts in the environment-resilience playbook, and trims the protocol body from 507 to 481 lines without dropping a single rule. Since v3.5.5 compliance no longer depends on model discipline alone, answering the 2026-09-21 incident report in which three sessions ran silently protocol-free and only a manual user audit caught it: a worklog activation hook turns the platform-mandated append-only work log — the one external anchor guaranteed to be read by every session and immune to continuation-summary compression — into a persistent activation trigger carried by its newest section; a compliance-sentinel pattern for polling watchers detects the incident's exact signature (an actively growing work log with no memory checkpoint) and alarms at the log tail; the bundled audit-compliance.sh gives the user a one-command external audit (Active-table hygiene, checkpoint-staleness signature, install-vs-lock version sanity, hook presence) with a PASS/WARN/FAIL verdict and exit code; and the skill description is hardened into an imperative invoke-now activation rule — revalidated blind at 40/40 on the 20-query trigger eval. Since v3.5.7 the self-heal closes the two gaps documented by a 2026-09-22 consumer incident (a container recycle restored skills/ from a stale pre-upgrade archive, silently rolling the install back while every bundled repair source was dead at once, and heal --check still reported CLEAN because it verified the stale manifest against itself): heal-skill.sh now cross-checks the ClawHub lock file — an out-of-band anchor that survives skills/ restores — and reports a DOWNGRADED verdict with a non-zero exit instead of a false CLEAN whenever the disk is older than the lock, still failing loudly after a repair that cannot reach the lock version; the sibling install location (skills/stellar-trail ↔ skills/@owner/stellar-trail) joins the repair sources so a clawhub update that only refreshed the owner-scoped copy can still heal the flat install the platform reads; a one-line vault self-arm hint is printed whenever both class-A vaults are empty (vault-sync.sh runs directly from the install directory); vault-sync.sh stamps the synced version and date into the vault README as an out-of-band marker; and release packaging enforces a version-consistency gate (body banner == skill card == integrity manifest) so a forgotten bump can never ship a self-inconsistent package. The whole chain is validated by a controlled drill replaying the incident end-to-end (a stale-archive restore with every repair source dead is reported DOWNGRADED with a hard non-zero exit and zero false-CLEAN claims, and a fresh sibling install heals the flat installation from the other clawhub layout convention, 14/14 assertions), and the bundled explorer launcher gained a deployment-freshness sync so served UI files can never silently lag the canonical release.

Since v3.5.8 the repair chain verifies the health of its own repair sources: a candidate source that carries a release manifest must match it tree-for-tree before it can be selected, so a poisoned canonical copy (a real 2026-09-22 platform-reset finding: an edit landed after the manifest regen, the corrupted source won version selection, was copied faithfully, and boot-heal failed at the worst possible moment) is skipped in favor of the next healthy source such as the class-A vault, an explicit env override is honored with a loud warning, and an all-poisoned candidate field fails hard instead of copying the corruption — while release packaging gains a symmetric tree-equals-manifest gate so a forgotten manifest regen after a last-minute edit can never ship a self-inconsistent package.

Since v3.6.1 the shipped package closes the consumer gap documented by the Task 55 field forensics (three confirmed failure modes on reset-prone sandboxes: skill files wiped because the platform packer excludes skills/ from the restore archive, services killed by a reset with no boot hook to revive them, and the activation chain broken because worklog.md was never created): the new bundled scripts/bootstrap-sandbox.sh arms the whole persistence layer in one command — it seeds a canonical copy under download/stellar-trail/ (a directory the packer preserves), installs a .zscripts/dev.sh boot hook that verifies the live skill installation against the release manifest and restores it from that canonical copy on every boot (one proven path per module, no redundant fallbacks, idempotent, offline, self-locating), seeds worklog.md carrying the activation hook, and scaffolds memory/ with a consent-pending marker the first session honors. The bundled explorer launcher is now self-locating (fixing an initialization-order bug in the packaged copy), the protocol body gained Activation rule 14 plus an M0 step that runs bootstrap --ensure at cold boot, and the heal-chain release history moved from the protocol body to the environment-resilience reference (progressive disclosure, body stays under 500 lines).

Since v3.6.2 the package fixes three consumer-experience defects reported by a fresh-install report from another sandbox (Installation & Explorer Report, 2026-09-25): the explorer launcher, run directly from the install tree (skills/stellar-trail/assets/explorer/), crashed with a FileNotFoundError before ever binding a port — its self-locating PROJECT resolved to the assets directory and explorer.py opened a PID file under a .zscripts path that was never created — so the launcher (v1.3) now detects the install-tree layout, copies itself plus the server and UI into the project's .zscripts/ directory, and re-execs from there (loop-guarded via an environment flag and layout detection, zero writes into the install tree, so heal drift stays zero); the heal script's last-resort manual fallback, which pointed at `clawhub update --force` — a dead route ever since the registry suspended the publisher account (under appeal) — now prints the verified GitHub reinstall route (git clone + manifest check, no login, no remote code execution) with the clawhub command noted only as a conditional alternative should the registry recover; and the external compliance audit's C1/C5 findings on a fresh CLI-only install (memory scaffold absent, activation hook not yet appended — expected post-install states, not violations) now carry a one-line bootstrap hint pointing at scripts/bootstrap-sandbox.sh, with the memory scaffold itself remaining consent-gated as before.

## Known Risks and Mitigations:

Risk: Always-on persistent memory can restore or retain project context across interactions without enough scoping or user controls.

Mitigation: v2.0.1 embeds these controls directly (section 4b): a cold-start consent gate with no silent initialization, a no-secrets data-minimization rule, per-project plain-markdown storage the user can inspect, and same-turn correct, redact, delete and purge commands.

Risk: Unchanged installation on shared machines or sensitive projects could expose unrelated prior context to later chats.

Mitigation: Avoid deployment in shared or sensitive environments; memory is scoped per project directory, stores work facts only, and the user may narrow, disable, or purge the memory half at any time as a locked decision.

Risk: Mandatory clarification and checkpoint behavior can conflict with quick-response expectations or with tasks that should not preserve state.

Mitigation: v2.0.1 rule 13 separates hurry pressure (compresses format, never cancels a phase) from an explicit owner opt-out ("disable the guardian"), which is recorded as a durable decision and honored for the requested scope.

Risk: The optional snapshot-repo.sh helper overwrites the platform's restore archive, and that archive is later extracted by the platform without member validation — a tampered archive could carry path-traversal members.

Mitigation: v2.2.1+ hardens every path that installs an archive: builds, staged copies, and post-swap finals are member-audited (absolute paths and any ".." components are hard-rejected; absolute-target symlinks are warned), and --restore-original is verified before swap so a corrupt or hostile backup is refused while the backup itself is preserved. v2.2.2 closes the build-time argument-injection vector: the entry list is passed NUL-separated via `tar --null -T`, so file names are never parsed as tar options (a file named `--use-compress-program=...` cannot make tar execute a command), dash-prefixed or newline-bearing names are skipped, and data-producing functions log quietly so diagnostics can never leak into the entry list. The script remains strictly opt-in (explicit user request only), backup-first, and reversible.

Risk: On continuation windows the platform injects an auto-generated summary without guaranteeing that the agent reads the worklog or memory files before its first response — the activation contract (load the body at the first turn) can fail exactly in the session that needs cross-session discipline most, and responses then run without protocol markers; a container recycle can additionally roll the installation back so the very defenses shipped to catch this (activation hook, audit script) are wiped together with the body (production-verified failure mode, Activation rule 11; consumer incident 2026-09-22).

Mitigation: v3.5.5 layers defenses that do not depend on model discipline — an imperative invoke-now description (blind-validated 40/40), a worklog activation hook carried by the newest section, a compliance-sentinel signature for watchers, and the bundled audit-compliance.sh one-command audit. v3.5.7 moves rollback detection to an anchor that survives skills/ restores: heal-skill.sh cross-checks the ClawHub lock file and reports DOWNGRADED with a non-zero exit instead of a false CLEAN, and the post-incident re-arm procedure (clawhub update --force, heal both install locations — the sibling location is now a repair source, vault-sync.sh --apply to re-arm the vaults) is documented in references/environment-resilience.md section 4. A platform-level on_session_start hook remains a registry roadmap item, not a guarantee.
