## Description:

Stellar Trail 🌠 defines a mandatory six-phase execution protocol and persistent memory lifecycle for agents so work can be classified, clarified, planned, executed, validated, reported, and restored across sessions. Phase 1 classification is grounded in a canonical Ground Base Knowledge (type taxonomy, language rules, complexity calibration, ambiguity registry, environment ground truths) so every decision cites a rule ID instead of intuition. Phase 5 validation runs five review layers (artifact verification, smoke, lint, request-vs-deliverable diff, regression) before anything is reported, and enforcement is dual-track: terminal-verifiable rules are executed via the bundled gate script (enforce-gates.sh), judgment rules stay as text mandates — a claimed-but-not-run gate is itself a violation. Since v2.0.1 the skill carries an explicit activation rule: a description in a skill list is not activation — agents load the full protocol body at the first turn of every session or continuation, then display auditable phase and memory markers on every response. Since the 2026-09-29 activation hardening the description is re-engineered from measured trigger behavior (scope claim first, invoke imperative immediately after — the combination that wins both task-type and greeting-type first turns), and a late mid-session load is a defined recovery event — Activation rule 16: immediate M0, an auditable LATE-ACTIVATION worklog note, and full compliance resumed from that turn — instead of a grandfathered non-compliance. Memory is user-controlled by design: plain-file storage, a cold-start consent gate, a strict no-secrets minimization rule, same-turn inspect, correct, redact, delete and purge commands, and an explicit owner opt-out that differs from hurry pressure (SKILL.md section 4b, rule 13). Since the 2026-09-29 checkpoint-discipline hardening, every checkpoint follows a fixed write order (snapshot rewritten before the ledger append, with a pre-append guard), long stretches take one checkpoint per completed artifact, and M0 detects and settles checkpoint debt — a worklog-tail vs snapshot-header mismatch — before any new work; the rules come from a real incident in which a session died between ledger append and snapshot rewrite. Since 4.1.0 (the slim-body release) the protocol body is a ~240-line read with deep procedures consolidated into a single on-demand memory-hygiene reference — the owner's field-proven diagnosis being that oversized read paths breed overthinking and compliance violations — while the M0 read path is hard-budgeted (worklog tail = last 3 task sections, MEMORY capped ~80 lines, gap-fill only below 95% recall), every task-sealing checkpoint deterministically refreshes the restore archive (snapshot-repo.sh --apply-auto), and the frontmatter description, all six scripts, the explorer, the watcher, and the boot hook are untouched.

Since v3.0.0 (formerly stellar-trails @ClawHub, renamed from workflow-memory-guardian) every phase marker carries a 🌠 — a visible, countable proof that the protocol is running.

## Known Risks and Mitigations:

Risk: Always-on persistent memory can restore or retain project context across interactions without enough scoping or user controls.

Mitigation: v2.0.1 embeds these controls directly (section 4b): a cold-start consent gate with no silent initialization, a no-secrets data-minimization rule, per-project plain-markdown storage the user can inspect, and same-turn correct, redact, delete and purge commands.

Risk: Unchanged installation on shared machines or sensitive projects could expose unrelated prior context to later chats.

Mitigation: Avoid deployment in shared or sensitive environments; memory is scoped per project directory, stores work facts only, and the user may narrow, disable, or purge the memory half at any time as a locked decision.

Risk: Mandatory clarification and checkpoint behavior can conflict with quick-response expectations or with tasks that should not preserve state.

Mitigation: v2.0.1 rule 13 separates hurry pressure (compresses format, never cancels a phase) from an explicit owner opt-out ("disable the guardian"), which is recorded as a durable decision and honored for the requested scope.

Risk: The optional snapshot-repo.sh helper overwrites the platform's restore archive, and that archive is later extracted by the platform without member validation — a tampered archive could carry path-traversal members.

Mitigation: v2.2.1+ hardens every path that installs an archive: builds, staged copies, and post-swap finals are member-audited (absolute paths and any ".." components are hard-rejected; absolute-target symlinks are warned), and --restore-original is verified before swap so a corrupt or hostile backup is refused while the backup itself is preserved. v2.2.2 closes the build-time argument-injection vector: the entry list is passed NUL-separated via `tar --null -T`, so file names are never parsed as tar options (a file named `--use-compress-program=...` cannot make tar execute a command), dash-prefixed or newline-bearing names are skipped, and data-producing functions log quietly so diagnostics can never leak into the entry list. The script remains strictly opt-in (explicit user request only), backup-first, and reversible.

Risk: On continuation windows the platform injects an auto-generated summary without guaranteeing that the agent reads the worklog or memory files before its first response — the activation contract (load the body at the first turn) can fail exactly in the session that needs cross-session discipline most, and responses then run without protocol markers; a container recycle can additionally roll the installation back so the very defenses shipped to catch this (activation hook, audit script) are wiped together with the body (production-verified failure mode, Activation rule 11; consumer incident 2026-09-22).

Mitigation: v3.5.5 layers defenses that do not depend on model discipline — an imperative invoke-now description (blind-validated 40/40), a worklog activation hook carried by the newest section, a compliance-sentinel signature for watchers, and the bundled audit-compliance.sh one-command audit. The 2026-09-29 hardening strengthens both ends of the same contract: the description is re-engineered from a 4-variant trigger eval (scope claim + invoke imperative + strengthened machine-content exclusion — measured on 20 queries spanning human first-turns and machine-generated non-targets), and Activation rule 16 converts any late mid-session load into a recovery event — immediate M0, a LATE-ACTIVATION worklog audit line, unmarked-turn output demoted to unverified input, and resumed compliance — so a late activation repairs the session instead of quietly lowering the bar. Since v3.6.7 rollback detection no longer depends on a repair chain: the M0 version-sanity alarm compares the installed banner version against the release recorded in memory, the watcher verifies the installation against its checksum manifest every ~10 minutes and alarms with the install command, and the boot hook's cache-replay restore rebuilds the installation from the canonical copy (which the platform archive preserves) with a no-downgrade version gate. The post-incident re-arm procedure is one command — re-run npx skills add hoshiyomiX/stellar-trail, then bootstrap-sandbox.sh --ensure --with-explorer --with-snapshot — documented in references/environment-resilience.md section 4. A platform-level on_session_start hook remains a registry roadmap item, not a guarantee.
