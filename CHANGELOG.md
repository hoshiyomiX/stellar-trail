# Changelog

## v5.4.1 — 2026-10-23 · explorer scalability fix + Miuix UI (owner work order: fix freeze on large file counts · migrate to miuix design)

**Why — the explorer froze/hung when the file count was large (owner-reported):** measured on a generated 22,000-file fixture, the v1.4 server paid **~420 ms of CPU + a 4.86 MB JSON payload on EVERY `/api/files` request** — and the UI polls that endpoint every 10 s (plus a client-side `JSON.stringify` of the whole payload just for change detection). Three compounding causes, each verified in code and by measurement: (a) `build_api()` re-walked and re-stat'd every file per request with zero caching; (b) `parse_tasks()` ran an O(tasks × files × section-bytes) substring scan per request — ~44 ms per task-section per 22k files, so an un-rotated 30-section worklog would pay ~1.3 s per poll; (c) the response embedded the FULL per-file arrays. Under the GIL the healthz probe and file downloads starved behind every poll (worst observed 42 ms, scaling linearly).

**What shipped:**

- **explorer.py v1.5 — scalable inventory serving:** ONE cached inventory shared by `/api/files` + `/api/list` (single-builder lock, 3 s TTL — a request burst shares one rebuild, never queues one rebuild per request; `/healthz` and `/file/` never touch the inventory and stay O(1)). `parse_tasks` rewritten to a token-index algorithm (O(worklog + files × tasks) set lookups; a file maps to a task when its name or label/rel path appears as a whole token — how names actually occur in worklog markdown). `/api/files` keeps its v1.4 shape but caps the per-root `files` arrays at `?max=` (default 1000) and adds `files_total`/`files_truncated` per root + `stats.type_counts`; `?max=0` omits the arrays entirely (the slim poll mode). NEW `/api/list` endpoint: server-side filter (q/type/task), sort (mtime/name/size × asc/desc), location (root), and pagination (`page`, `per_page` ≤ 500) — the response is bounded by `per_page`, never by inventory size.
- **explorer-ui v4.0 — Miuix (HyperOS) redesign, owner-ordered migration to the miuix design system** (compose-miuix-ui/miuix is a Kotlin/Compose library; the explorer's zero-dependency Python-stdlib + single-file web stack cannot run it — the migration ports the DESIGN SYSTEM: the color roles are verbatim from miuix `Colors.kt` lightColorScheme()/darkColorScheme() — primary #3482FF/#277AF7, HyperOS surfaces (light: #F7F7F7 page + white cards; dark: #242424 page + black cards), tertiaryContainer tints, windowDimming scrims). Component vocabulary: frosted TopAppBar, SmallTitle sections, squircle cards, SearchBar pill, TabRow chips, segmented controls, Snackbar, FAB, spring motion. All v3.4 features preserved (tiles, task rail, type chips, sort, grid/list, preview dialog incl. markdown/JSON rendering, copy-path, static-copy graceful mode + manual live-recovery, adaptive dark/light, zero-dependency, fully English, official Material Icons verbatim). **Client-side scalability:** the 10 s poll fetches only the slim `/api/files?max=0` (~2 KB), browsing goes through paged `/api/list` (100/page with a pager), and list refresh happens only when the server reports the inventory changed (`inventory_built`) — no more full-payload polls or client-side whole-payload hashing. Theme persistence migrates `md3-theme` → `miuix-theme` (old key honored as fallback).
- **Owner's locked formatting decision D10 amended by this explicit order:** the MD3-Expressive skin is replaced by the Miuix design language; the locked STRUCTURE survives (English UI, compact type, the four release-health tiles with official icon glyphs, sidebar-style task rail, no hero/bento revival).

**Measured results (22,000-file fixture, before → after):** `/api/files` warm 420 ms → 4.5 ms (slim poll 1.99 KB / ~1.2 ms); `parse_tasks` 132 ms → 24 ms; healthz worst-during-build 42 ms → 4.2 ms; a burst of 20 mixed requests during a cold rebuild: worst 352 ms, all served. UI at 22k files: first page renders 100 cards, pager 1/220, server-side search/filter/sort/paging all sub-100 ms, zero console errors (agent-browser + VLM visual verification, both themes).

**Verification:** task30 stress suite (fixture generator + baseline + 15/15 semantic/concurrency checks) · browser validation on the 20k fixture (render, search, chips, pager, task filter, modal preview, theme, static-copy logic, 0 page errors) · check-skill 7/7 (description untouched, 877/1024, wording-frozen) · audit-compliance PASS pre/post promotion · manifest 18/18 · three-tree sync + live :3000 smoke · `bash -n` / `node --check` on touched code.

## v5.4.0 — 2026-10-21 · silent-work sentinel + ALERT surface (2026-10-21 incident hardening, owner-filtered)

**Why — the first documented field incident of the cross-session skip class:** between protocol sessions 94→95 of a deployment container, at least two continuation sessions did real, high-risk work (build-4 implementation, release packaging, on-device deploy guidance) with ZERO protocol compliance — no banner, no checkpoints, no worklog writes. Every machine sentinel stayed silent BY DESIGN: the compliance sentinel triggers on "worklog growing without a checkpoint", and these sessions wrote nothing, so the worklog never grew (last alarm 23:14 the night before; incident window 04:19–05:25; zero alarms). The USER caught it, not the machine — alarms wrote only to files a compliant session would read (the guard-that-cannot-wake-the-guard paradox). The owner's selection criterion for the fix package: **evidence-backed mechanisms only; assumption-based proposals rejected.**

**What shipped (each keyed to a field-verified failure):**

- **Watcher duty 6b — silent-work sentinel (v2.3):** alarms from DISK evidence, not worklog growth — WORK-SILENCE (workspace/ scripts/ download/ artifacts outrunning the last checkpoint by >30 min; default env-tunable) and EVIDENCE-PENDING (upload/ user evidence unprocessed by any logged session for >2 h) — the exact forensic signals the incident was reconstructed from. 1 h debounce per class; the canonical copy, node_modules and the ALERT file itself are excluded (no self-trigger); the inner daemon block stays single-quote-free (C11).
- **`download/ALERT-ACTIVE.md` — the user-visible alarm surface:** the watcher writes/refreshes it while any class is active (WORK-SILENCE · EVIDENCE-PENDING · COMPLIANCE-STALE) and removes it on all-clear; it survives container restores (download/ is packer-preserved) and appears in the user's file list — closing the alarm-visibility paradox. Excluded from the duty-1 hash so an alarm never kicks the boot hook.
- **M0 artifact-freshness sweep + ALERT lift:** every session start now compares the newest work-artifact mtime against the Checkpoint-at header — artifacts ahead by >30 min = UNLOGGED WORK → rule-6 unverified-input posture, settle from disk, report the conflict. Detection at every session start, watcher-independent.
- **audit-compliance `silent-work` check + watcher duty 8 (~6 h periodic audit, epoch-gated):** the audit previously ran only at major checkpoints/manual calls; its verdict now lands in watcher.log as greppable history (FAIL also alarms the worklog), and the new check carries the incident class into every scheduled and manual audit.
- **Documentation of the incident as field evidence:** environment-resilience §6b case study (timeline, wrong-signal analysis, what caught it, what recovered it, what changed); README "Activation, honestly measured" gains the incident as first field proof of the description's structural limit + the full defense-layer map + the owner-audit tip (the LAST layer is the owner's eyes — the banner check caught this incident) + the honest note that a pre-response hook has no harness API.
