## v5.4.6 — 2026-10-24 · explorer UI v4.3.1 engine-proof deadlines: the startup-freeze class reproduced and killed (owner retest: still hangs at startup, only the header clock running)

**Why — the v5.4.5 owner retest failed with a NEW signature (freeze AT STARTUP, only the header clock running, UI frozen):** v4.3's fetch deadline existed ONLY via AbortController — engines without it (the owner's Android browser class, older WebView engines) got NO deadline at all, so both boot fetches hung forever: eternal spinner, no error, no reconnecting chip, while the independent header clock kept ticking. v4.3's own code comment said "degrades silently on ancient engines" — and the v5.4.5 hangtest never exercised that path (its Chromium always has AbortController): the blind spot. Server healthy throughout; the defect was purely client-side, engine-class-specific.

**What shipped:**

- **explorer-ui v4.3.1 — engine-proof deadlines:** every fetch now carries a deadline on EVERY engine (a Promise.race backstop rejects at ms+250 even when abort() is impossible — AbortError-named, so every existing catch path treats it identically; when abort works it fires first and frees the socket, making the backstop a no-op); an 8 s **boot watchdog** guarantees the honest reconnecting state no matter what the engine does to the fetches (flips the UI, un-wedges a stuck in-flight guard, keeps probing); **socket conservation** on engines that cannot abort (auto-polling stops after 3 consecutive failures — each unabortable poll holds a socket, and the ~6-slot HTTP/1.1 per-origin pool must survive for the wake probes + Rescan); **visible build markers** (the app-bar version chip reads "UI 4.3.1" until explorer.py answers, the error card carries the build — the next retest is self-diagnosing: a stale cached build is identifiable at a glance); and **cold-start list recovery** — the first successful meta poll after a failed boot now reloads the file list (a real recovery hole caught live by the new fixture before the owner could hit it).
- **hangtest extended 19 → 41 checks** (`scripts/task37-hangserver.py` + `task37-hangtest.sh`): a new `starthang` mode (the page serves while the APIs hold — the owner's startup view) plus AbortController-STRIPPED page variants served on :3162 (v4.3 control = the owner's engine class) and :3163 (v4.3.1 on the same stripped engine).

**Measured — the owner symptom reproduced byte-exact, then killed** (41/41): the v4.3-noAC CONTROL under starthang shows the owner's exact view — clock ticking across samples, eternal "loading file inventory…" spinner, NO reconnecting chip, footer frozen at "loading…", 2 boot-fetch sockets held FOREVER (no deadline, no abort — measured from the server side), zero console errors: a silent freeze. The v4.3.1 FIX on the same stripped engine shows the honest chip within the 5.25 s backstop, the error card with its build marker, bounded held sockets (auto-poll stops after 3 fails), then FULL RECOVERY 1 s after the focus wake-probe (8 cards, fresh scan record, the build chip flipping to the live skill version); the modern engine shows no regression (abort still frees sockets — 0 open — and recovery is intact); and the entire v5.4.5 matrix (phases 1–7) stays green.

- **Version 5.4.6** (banner constants, integrity.version, skill card; explorer server v1.6 / UI v4.3.1 / launcher v1.5).

## v5.4.5 — 2026-10-24 · explorer UI v4.3 fetch resilience: the popup-freeze class reproduced and killed (owner order: fix load data + re-enable file scan)

**Why — the owner's clarification answers locked the root cause (freeze AFTER content renders · recovers only after a minute+ · opens during active chat):** the platform suspends the sandbox between chat turns, and a suspended origin answers NEITHER data NOR connection errors — so the v4.2 UI's no-timeout 10 s polls (`setInterval(loadMeta,10000)`, zero AbortController, the connection-lost banner firing only on fetch ERRORS) stacked until the browser's per-origin connection pool exhausted (HTTP/1.1 ~6) and the popup froze totally: no error, no banner, no self-recovery until the next chat message woke the sandbox and drained the queue. The server was measured HEALTHY throughout (inventory fresh, warm slim poll 4.5 ms, guard 5.4.4 in_sync) — the defect was purely client-side. Owner go-ahead: "perbaiki bagian load data index.html of task file manager & enable file scan kembali".

**What shipped:**

- **explorer-ui v4.3 — fetch resilience for the Miuix dashboard (the load-data fix; visual identity unchanged per D10):** every fetch carries an AbortController deadline (5 s polls/list, 10 s previews, graceful degradation on engines without AbortController); the 10 s poll loop is replaced by a self-scheduling, in-flight-guarded loop (`pollOnce`/`schedulePoll` — polls NEVER stack) with failure backoff 10→20→40→60 s cap; a suspended sandbox now surfaces as an HONEST state — an app-bar reconnecting chip plus a footer that says what happened and how to wake it ("the sandbox may be asleep — it wakes when you send a chat message") instead of the silent hang; visibility/focus/online wake probes bypass the backoff (refocusing the popup right after a chat message is exactly when the sandbox has woken) so full-speed scanning — the "file scan" — re-enables itself the moment data returns; file previews time out with an explanatory message; and a manual **Rescan** button (app bar) forces a scan with a completion report ("Scan complete — N files @ HH:MM:SS"), the owner-visible file-scan switch. Static-copy probes ride the same bounded loop. Two STALE version strings repaired: the UI footer still said "UI v4.1" (v5.4.3 shipped v4.2 without bumping it) and the guide's component table said "UI v4.1" — both now v4.3.
- **explorer.py v1.6 — unchanged this release** (re-measured healthy on live roots: 40 files, warm slim poll ~4.5 ms, inventory rebuilding on schedule; backlog 64 intact). The release ships the UI patch through the standard pipeline: three-tree promotion, manifest regen, full gates.

**Measured — the FIRST in-container reproduction of the freeze class** (`scripts/task37-hangserver.py` + `scripts/task37-hangtest.sh`, an accepts-never-responds origin = the suspension seen from inside the browser; 19/19): the v4.2 CONTROL under a hanging origin stacks **6 held API sockets by 70 s** (per-origin pool exhausted = the total freeze), its footer keeps claiming "auto-refresh every 10 s" (the dishonest healthy state — no error, no banner: exactly the owner symptom), and after the origin returns it does NOT recover (held sockets never complete, the list stays stale). The v4.3 FIX under the same origin holds **≤1 open API socket at every sample** (5/5), shows the honest reconnecting chip+footer (5/5), throttles probing via backoff (4 API hits in 35 s), then recovers **1 s after a focus wake-probe** — auto-refreshing the list to changed data (content_sig) and a fresh scan record — and the manual Rescan reports "Scan complete — 8 files @ …"; zero page errors across the whole run. Evidence screenshots: ui-v43-reconnecting / ui-v43-recovered / ui-v42-frozen.
