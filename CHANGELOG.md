## v5.5.1 — 2026-11-01 · harness-hooks §9b: refresh-if-byte-identical seeding — the Task 49 audit gap closed (owner order — Task 50, ref #49)

**Why — the Task 49 AGENTS.md criticality audit found a real version-drift class in bootstrap §9b:** the module seeded CLAUDE.md/AGENTS.md at the project root create-if-absent ONLY — an unmodified root seed was never refreshed when the template changed across releases, while the --status label "SEEDED (managed)" overstated management (a "managed" seed that no longer tracked its template). Risk was LOW today (the template is instruction-level, version-agnostic, and byte-stable since 2026-10-08) but the class was real: any future template improvement would silently strand every existing install on the old bytes. The owner ordered the fix executed ("eksekusi perbaikan §9b").

**What shipped:**

- **seed-hashes.txt registry (assets/harness-hooks/, NEW):** one sha256 per template version ever shipped, one line per file. Runtime semantics: a root CLAUDE.md/AGENTS.md whose hash is registered (but differs from the current template) is an UNMODIFIED seed of an older release — bootstrap refreshes it to current; a hash listed nowhere is a user-edited file — never touched. The registry rides the checksum manifest like every payload file; the maintenance rule (a release that changes a template appends the new hash in the same release) lives in its header — the audit's "release-checklist line" option folded in.
- **bootstrap-sandbox.sh §9b (module paths):** module-on now has four states (seed · current-never-rewritten · REFRESH-registered-old-seed · keep-user-file) · --without-harness-hooks removes OLD-version unmodified seeds too (registry-listed), not only current-template-identical ones · the --status display gains a third state (STALE SEED — refresh on next --ensure), making "managed" mean actually-tracked · header + module-list comments updated.
- **bootstrap-sandbox.sh (boot chain + helper):** the dev.sh step-7 heredoc carries the same refresh inline (project-root files are not in the packer preserve list) · new `seed_known` helper (awk registry lookup; registry absent = pre-v5.5.1 install = safe old behavior).
- **SKILL.md §6 + skill-card.md + environment-resilience.md:** the hooks semantics text updated everywhere it is described — create-if-absent + refresh-if-byte-identical, registry-tracked, user-edited files never touched.

- **Version 5.5.1** (banner constants, integrity.version, skill card; explorer.py v1.7 / Miuix UI v4.4 / watcher v2.3 — untouched, pure bootstrap tooling + docs).

## v5.5.0 — 2026-10-31 · seal silence rule + Max shield + D11 memory-source preference + Pending Plans persistence (owner order — Task 47, ref #46)

**Why — the owner's 3-item order "Fix bug & improve skill", clarified through the 7-question batch and locked:** (1) delivered tasks lingered in WAITING when the owner never sent a confirmation — the seal should happen when the next session runs without one, and sealed tasks must never be picked up by an LLM and re-run duplicately; (2) stellar-trail's memory management must outrank the platform worklog + context summary (three consecutive stale-specimen sessions narrated sealed work as pending — the summary layer lies about what is alive); (3) a pending plan must survive context loss — plans lived only in the conversation and died with it. **What shipped:**

- **The silence rule (SKILL.md §4 S1 + §3 M0 triage + the pickup table + QRC; memory-hygiene S1/S3/H3/M0-step-3):** a WAITING (acceptance) row for a verified delivery that is still unconfirmed when the next session's M0 runs seals AT that M0 — verdict `SEALED-AUTO` on the Task-ID line (greppable like every verdict; the artifact verification still applies). Acceptance now explicitly includes the implicit form: a later owner message in the same session that builds on the delivery without objection (the dogfood pattern Tasks 42-46 already used). An unaccepted delivery never waits longer than one session boundary.
- **Max shield (H4 expanded + §9 violation + QRC + a NEW audit-compliance check):** a sealed task is never re-executed, re-planned, re-delivered, or continued — and any plan or response that names a sealed Task ID as pending work is REFUSED and REPORTED before execution. One-ID-one-table law: a Task ID exists in exactly ONE of Active/Sealed; the new sealed-shield audit check FAILs on any Active-vs-Sealed ID collision (an ID-column hit; ref mentions in descriptions stay legal — H4 revisits open a NEW task).
- **D11 memory-source preference (§0 platform alignment + locked decision):** stellar-trail's memory management OUTRANKS the platform worklog + context summary — memory FILES are the single source of truth; platform summaries stay quarantined hints (H8-H13); worklog.md stays single-writer stellar-trail-owned. - **Pending Plans (SESSION-STATE template + §2 Phase 3 + §3 M1 + R2; memory-hygiene template/M1/R2):** a new per-ACTIVE-task block — full step list with done/pending statuses + next action + blockers — persisted at the Phase-3 M1 and rewritten at EVERY M1; step completions and deferrals are checkpoint-worthy state. R2 resumes reconstruct from the persisted plan; a mid-plan context loss now costs at most one step, never the plan.
